# 仕様書：AI分析の質向上 — 体温×KPIの紐付け改善

> ステータス：設計・仕様（実装前）
> 対象：`src/app/api/ai/analyze/route.ts`（体温とKPIの相関分析エンジン）
> 目的：ボイスチェック（体温）とKPI（成果）の紐付け精度を上げ、AI提案の質を高める

## 背景・課題

現状の `analyze/route.ts` は「体温とKPIの相関」をAIに分析させているが、以下の構造的な弱点がある（コードレビューで確認済み）。

1. **同月で体温とKPIを突き合わせている**：体温は先行指標、KPIは遅行指標。今月の体温×今月のKPIだと本当の関係を取りこぼす／同月ノイズを拾う。
2. **11問の体温を単一の平均（avg_pulse）に潰している**：設問（カテゴリ）ごとにKPIへの効き方は違う（摩擦・速度は短期業務に、安全性・エンゲージメントは長期に効く）。平均で潰すと示唆が鈍る。
3. **小サンプル（例：3人部署）**：単月の avg_pulse は1人の気分で乱高下し、相関が信用できない。

## 確定方針

### ① 体温を「3ヶ月トレーリング平均」にする（先行性＋サンプル増を同時に解決）
- 体温（pulse）を **当月＋過去2ヶ月＝3ヶ月の移動平均** で算出する。
- これにより 3人部署でも実質9件相当となりノイズが減り、直近の累積的な組織状態を反映できる。
- **当月KPIと突き合わせる**（「直近3ヶ月の体温 → 今の成果」）。翌月ラグは取らない（解釈明快・初期データでも動く・先行性は移動平均に自然に含まれる）。

### ② 設問（カテゴリ）別スコアをAIに渡す
- 単一の avg_pulse ではなく、**設問（カテゴリ）別の体温スコアの内訳**をAIに渡す。
- 標準11問はカテゴリがほぼ1対1（engagement / speed / transparency / friction / safety / clarity / feedback / workload / impact / challenge / readiness）。カテゴリ名（または設問テキスト）をラベルとして付与する。
- カスタム設問（`company_id` 指定・カテゴリなし）は「カスタム」扱いで個別に含める。
- 設問別スコアも **①の3ヶ月トレーリング窓** で算出する（サンプル頑健性のため）。

## 実装詳細（`src/app/api/ai/analyze/route.ts`）

### 体温の集計を変更
- 現状：`historicalContext` 各月および per-dept で、その月の `survey_answers` スコアの単純平均を `avg_pulse` にしている。
- 変更：相関分析・提案に渡す per-dept / 全社の「現在の体温」を、**最新月＋過去2ヶ月のスコアを母集団とした平均（トレーリング3ヶ月）** にする。
  - 月形式：`survey_responses.recorded_month` は **YYYY-MM**。窓は最新月とその前2ヶ月。
  - データ取得範囲は既存で過去複数月を取得しているはず（1m/3m/6m/1y のhistorical context があるため）。不足する場合は取得範囲を3ヶ月以上に広げる。
- KPI側：`kpi_details` は**当月（latestMonth）のまま**。トレーリング窓は体温側だけに適用する。

### 設問別スコアの追加
- per-dept ごとに、トレーリング3ヶ月窓で **設問（カテゴリ）別の平均スコア** を計算し、プロンプトに渡す。
  - 例：`{ category: 'friction', label: '調整・根回し', avg: 2.1 }` のリスト。
  - カスタム設問は `category: 'custom'` 等で設問テキストをラベルにする。
- 全社レベルでも同様の設問別内訳を渡せると、横断的な弱点（全社的に「速度」が低い等）が見える。

### プロンプトの更新（重要）
- AIが体温を「単月値」ではなく「**直近3ヶ月の移動平均**」と理解するよう、プロンプト内の体温の説明を明記する（誤って二重にラグを解釈しないように）。
- `"correlation"` の指示を「直近3ヶ月の体温（設問別内訳含む）が当月のKPIにどう表れているか」に具体化する。
- per-dept の投入行（現状 `【部署名】体温:X KPI:... 人件費:...`）に**設問別の低スコア項目**を併記する。

### 小サンプル時の節度（②の副次）
- トレーリング窓でも回答総数が少ない部署では、AIが断定的な因果を語らないようプロンプトで抑制する（「サンプルが少ない場合は仮説として提示」等）。
- 既存の匿名性ガード（3名未満は非表示）の思想と整合させる。

## 留意・エッジケース
- **データが3ヶ月に満たない新規会社**：利用可能な月（1〜2ヶ月）で窓を組む。エラーにしない。
- **トレーリング窓内に回答が全くない部署**：従来どおり体温なし（avg=null）として扱い、相関に含めない。
- **`system_settings` のAIプロンプトを変更する場合**：CLAUDE.md のルールに従い、変更内容とJSON構造をPR説明に記載する。
- DB変更・migration は不要（既存テーブルの集計方法の変更のみ）。

## レビュー観点（Claude）
- トレーリング窓が「最新月＋過去2ヶ月」で正しく組まれ、月跨ぎ（年跨ぎ）でズレないか
- 体温はトレーリング、KPIは当月、というペアリングが意図どおりか（混線していないか）
- 設問別スコアの集計で `axis_id` や重複回答の二重計上が起きていないか
- カスタム設問（カテゴリなし）が欠落・誤集計していないか
- プロンプト変更で体温が「移動平均」と明示され、AIが二重ラグ解釈しないか
- 既存の historical context（trend表示）を壊していないか
